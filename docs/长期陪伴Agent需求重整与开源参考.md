# 长期陪伴 Agent：需求重整与开源参考

状态：待用户确认的调整方案，不代表已实现。调研日期：2026-10-22。

## 1. 已确认的真实需求

- 不是另一套报告工具，而是能持续了解用户、跟进建议的个人 Agent。
- 邮件是主要复盘入口：结合过去一段时间的事实、用户目标、上次建议与反馈，提出一两条可执行的调整。
- 客户端 Agent 能按需使用同一份长期记忆，不必让用户重新讲背景。
- 飞书可以自主发现值得关注的变化后主动联系用户，不只按日历定时发送。
- 页面由工程侧自行排查、统一优化，不要求用户逐项指出问题。
- 飞书主动发送的许可不等于读取全部聊天、资料或推断健康人格的许可。

### 2.1 经官方资料核实的要点

- [OpenClaw 自动化](https://docs.openclaw.ai/automation/cron-vs-heartbeat)：定期监测与周期报告都可以是普通自动任务，检查、上下文与投递策略分别管理；无事时允许 `NO_REPLY`。
- [OpenClaw Heartbeat 迁移](https://docs.openclaw.ai/gateway/heartbeat)：当前在线文档描述 Heartbeat 迁为普通可编辑任务，有活动时间、空闲运行、明确 owner 私聊投递等策略。搜索结果中的旧 GitHub 文档与在线文档存在版本差异，不能混用为同一版本事实；实施时应固定 commit 复核。
- [OpenClaw 记忆](https://docs.openclaw.ai/concepts/memory)：区分稳定用户信息、长期记忆与每日工作记录。这里只参考分层，不照搬其启动时加载完整记忆的做法。
- [Letta memory blocks](https://docs.letta.com/guides/agents/memory-blocks/)：多个 Agent 可共享一个记忆块；其常驻上下文机制不符合本项目现有硬预算要求，需要改成按需检索。
- [Mem0 memory operations](https://docs.mem0.ai/core-concepts/memory-operations)：区分托管平台与自托管 SDK，提供用户作用域和过期元数据；本次在线文档描述 additive storage，不能把旧文章里的 ADD/UPDATE/DELETE 全部当成当前默认语义。
- [nanobot 主仓库](https://github.com/HKUDS/nanobot)：声明支持长期记忆、自动化与多聊天入口；具体 Dream/飞书行为仍应固定版本逐文件核查后再借鉴。
- [nanobot 问题 #2582](https://github.com/HKUDS/nanobot/issues/2582)：用户报告无事时仍反复推送状态消息。这是问题记录，不代表当前版本一定仍有缺陷；它说明不能仅依赖自由文本模型判断是否打扰。

结论：重点参考 OpenClaw 的产品运行方式、nanobot 的轻量边界，结合 Letta/Mem0 的记忆思想；暂不替换 Java + AgentScope，也不新增 Python 常驻服务或向量数据库。

## 3. 当前实现与需求的差距（源码静态核查）

- `review/ReviewCoachService` 面向报告作业；`server-agents/context` 与 `server-feishu` 未发现复盘域接入，当前不具备本需求中的共享召回或自主飞书推送。
- 现有事实采集最多覆盖 31 天，与设置中 180 天窗口的用户预期不一致；“允许回看”不等于“真的回看”。
- `ReviewSettings.tsx` 同页铺开范围、授权、目标、预览、采集、清除、历史、全部建议与观察，主要路径被运维操作淹没。
- 页面直接实现原生 input/select/textarea/checkbox 和状态徽标，而项目已经有 TextInput、Select、Toggle、Badge 等公共组件；视觉与交互难以统一。
- 使用一个 Promise.all 加载所有区块，一个请求失败会阻止首次整页数据展示；读取全模型配置还会把不必要的密钥字段带入组件状态。
- 刷新与每次操作后的整页重载会覆盖尚未保存的表单；查看详情也触发“读取成功”消息和整页刷新。
- 预览硬编码日报和昨天，不能自然服务只开启周报的用户；日期用 UTC 字符串截取，可能偏离用户自然日。
- 反馈页面同时堆叠多个决策和结果按钮，甚至向暂缓状态展示结果入口，与后端“结果必须先采纳”约束不一致。

上述结论来自源码，不宣称已做浏览器视觉或真实邮件投递验证。

## 4. 目标体验

### 邮件：一封能延续上次话题的复盘

1. 本周期值得注意的变化，注明数据缺口，不复述全部账表。
2. 上次建议现在怎样了：客观趋势与用户反馈分开呈现，没有反馈就写“尚不清楚”。
3. 下一步最多一两件，说明理由、最小行动和检查时间；也允许本周期无需新增建议。
4. 能在客户端或已绑定飞书继续讨论同一条建议，而不是重新描述背景。

日报关注当天/近期调整；周报观察连续模式；月报检验方向和目标，不把同一模板换个时间范围。

### 客户端：自然延续，不全量塞记忆

用户询问学习、消费或目标进展时，Agent 通过唯一上下文组装入口召回相关目标、有效事实、已采纳建议和用户纠正。给出来源和时间；旧事实不可覆盖新纠正；候选观察明确标为推测。聊天模型与自动复盘模型可以不同，共享记忆不等于共享外发权限。

### 飞书：有值得说的事才发

来源事件或低频检查 → 提取变化候选 → 校验证据与新鲜度 → 判断相关性和可行动性 → 预算/免打扰/去重 → 固定绑定私聊投递。

模型可以提出候选，但不能越过确定性投递门禁。没有新变化、信息不足、已提醒、用户已拒绝、建议在冷却期时保持安静。不承诺“全天监控”：只有后端在线才能发现和投递。

## 5. 共享记忆与主动运行架构建议

- 保留四层：事实、用户确认的目标/偏好、候选观察、建议及反馈；都有 owner、来源、时间、版本与有效性。
- 建立权威共享检索服务，由网络层提供领域实现，agents 层定义中立读取契约；不让 agents 反向依赖 network，也不让飞书模块读取复盘数据库。
- 客户端上下文仍接入 ConversationContextAssembler，增加有硬 Token 预算的来源；群聊不自动召回私人记忆。
- 复盘、聊天、飞书使用相同记忆 ID；不是复制三套 MEMORY 文件。纠正或删除在所有读取入口立即生效，不自动改写用户画像。
- 自动分析权限、聊天检索/外发权限、飞书投递权限分别表达；不能沿用报告授权隐式扩大用途。
- 主动候选与发送记录持久化；证据指纹和主题用于去重，投递状态独立于生成状态。发送结果未知不得自动重发。
- 建议默认：飞书一天最多 1 条主动消息、同主题 72 小时冷却、22:00–09:00 免打扰；这些是待确认的初始值，不是现有行为。
- 自动模型费用预算与通知上限分开：不发送也可能产生分析费用，页面必须如实说明。

## 6. 页面重整建议

保留一个“长期陪伴”入口，与现有“个人上下文”设置协调职责，避免让用户理解两套长期记忆。

- **概览**：是否运行、下次邮件、飞书状态、当前目标、最近一条跟进；异常给出可执行的修复入口。
- **开启与投递**：邮件周期/时间、飞书绑定/免打扰/频率；复用现有任务与邮件配置，不重新维护第二份权威日程。
- **记忆与目标**：我明确告诉 Agent 的事、有效建议、待确认观察；历史详情分页或抽屉展示，不在设置主页面全部铺开。
- **隐私与高级设置**：可读取范围、允许用途、固定后台模型、费用预算、暂停、撤销、导出/清除。清除放危险操作区。

首次启用集中完成“选范围 → 选用途与渠道 → 确认”，之后常用的是暂停/继续，不要求频繁操作授权表。扩大用途、范围或模型接收方仍需确认。

所有表单复用公共组件；加载与失败按区块隔离；保存不重置其他草稿；不对普通查看弹成功提示。先补组件状态与自动化交互验证，再按需要做视觉验收。

## 7. 重做顺序与验收

1. 先修正当前误导与运行风险：日期、授权真相、预览边界、撤销后的基础邮件收尾、证据明细；不把测试通过等同产品完成。
2. 建共享记忆读取与纠正失效闭环，验证客户端在同一目标上能延续邮件建议。
3. 建主动候选/门禁/outbox，并接飞书固定私聊；用合成事件与假模型验证，不发送真实消息。
4. 重做邮件内容和统一设置界面，区分日/周/月。
5. 用至少 30 个合成场景验收：有变化才提醒、无事安静、跨渠道同一记忆、纠正后不再引用、群聊不泄露、费用和频率受限、重启不重复发送、离线不假装运行。

本轮只提交调研与待确认方案，不改变业务代码，不启用任何功能，不推送远程。用户确认方向后再更新强制 DOX 契约并实施。
