# 自动长期记忆复盘教练实施方案

> 状态：已开始分阶段实施，当前仅完成后端基础能力，详见第 17 节；实际隐私授权仍须用户在应用中明确确认。
> 模型执行器、反馈闭环、自动邮件与设置界面尚未接入，当前 `generationAvailable=false`。不会因部署此代码自动调用模型或初始化用户模型配置。
> 前置调研：[长期记忆复盘教练开源调研](长期记忆复盘教练开源调研.md)。

## 1. 产品目标与技术选择

建设一个随日报、周报、月报自动运行的长期复盘教练：记得用户确认的目标、可追溯的历史事实、此前提出的建议及反馈，依据新证据调整意见，而不是每次重新点评一份邮件。

**推荐路线：AgentScope Java + 当前 SQLite + 自建领域化记忆与反馈闭环。** 首版不增加 Python 服务，不接管聊天 Agent，不引入 Letta 运行平台，不依赖向量数据库；借鉴 Letta 的分层记忆与 Reflexion 的反馈机制。Mem0 仅作为以后有评测依据时的候选，不提前制造一套空的远程检索接口。

“有道理”的工程定义是：有证据、尊重目标与约束、区分事实和推测、不重复骚扰、行动足够小、以后能检查。不能保证每条建议都正确，也不宣称模型通过记忆自行训练或升级了权重。

### 1.1 首版包含

- 自动评审授权、选择固定模型、日报／周报／月报独立开启。
- 冻结当期结构化事实，读取有限历史趋势和复盘记忆。
- 明确目标、建议跟进、观察与纠正机制；从第一版就有长期记忆，不先做无记忆点评。
- 规则选题、单次模型生成、结构与证据校验、邮件附加区、失败降级。
- 应用内复盘历史、采纳／不适合／纠正／检查结果、暂停、导出与清除。
- 有上限的历史摘要初始化与可解释召回；不要求用户攒满一个月数据才能使用。

### 1.2 首版不包含

- 自动读取全部聊天、资料正文、流水备注、完整账号或银行标识。
- 自动创建待办、修改财务数据、代用户采纳建议、后台改写 PROFILE.md。
- 自我修改系统提示词或代码、无限多 Agent 讨论、无限自我反思循环。
- 邮件回复解析、免登录反馈链接、浏览器自动操作、心理诊断、人格评分、投资推荐。
- 修复历史已删除账户档案缺失。该限制属于财务事实来源，AI 不能弥补。

## 3. 用户体验：自动执行，但用户仍掌控理解权

### 3.1 开启流程

在“任务设置 → AI 长期复盘”中：

1. 阅读数据范围、模型供应商及“自动运行可能产生费用”的说明。
2. 选择已有模型配置中的固定 Provider ID 和模型名，不保存新的密钥副本。
3. 分别选择日报、周报、月报；选择允许的统计域与最多回看 180 天。
4. 可选填写最多 3 个当前目标、衡量方式、约束、希望检查的时间；没有目标时不虚构目标。
5. 独立确认自动处理授权，并保存带 revision 的配置；所有旧任务默认关闭。
6. 每个报告任务再设置“附加 AI 复盘”。有效开关 = 全局开启 ∧ 该周期开启 ∧ 任务开启 ∧ 有效授权。

复制任务不复制授权，复制出的任务 AI 开关默认关闭。切换后端／重装不能悄悄产生新授权；授权以当前后端保存的记录为准，前端缓存不是权威事实。

### 3.2 邮件与应用内呈现

| 类型 | 主要历史窗口 | 复盘重点 | 建议数量与文字上限（建议默认值） |
| --- | --- | --- | --- |
| 日报 | 近 7／28 天 | 当天值得关注的变化，之前一个小行动的新进展 | 0–1 条；约 250 个中文字符 |
| 周报 | 近 4／12 周 | 行为是否重复、阻碍、采用过的方法是否值得保留 | 0–3 条；约 600 个中文字符 |
| 月报 | 近 3／6 月 | 目标与投入是否一致、资产与收支结构、下月取舍 | 0–3 条；约 900 个中文字符 |

窗口是候选范围，不代表所有内容都进入模型。数据不足时写明有效样本范围，不硬凑趋势。中文字符上限与模型 Token 上限分别约束。

邮件基础数据区保持原统计、收入绿／支出红；新增“AI 长期复盘”区：本期观察、历史联系、建议跟进、小步实验、依据编号与数据边界。不要给整个人生打分，也不要强行每天找问题。

反馈在应用内登录态完成。邮件只提示“在应用 → 任务 → 复盘历史查看与反馈”，首版不在邮件中放免登录写操作链接。桌面系统通知继续使用基础报告摘要，不播放长篇 AI 结论。AI 不影响久坐等非报告提醒。

“预览（不发送）”仍只生成基础邮件，不因打开预览触发模型或写长期记忆；若已有同周期复盘，可只读展示。另设明确的“生成 AI 预览”，展示费用与数据范围，使用临时结果，不发送邮件、不产生建议承诺；不能把用户选择自动模式偷换成每次手动确认。

### 3.3 反馈与可控记忆

- 建议可标记“采纳／不适合／暂不决定”；采纳时允许修改动作与检查日。
- 到检查日只核对已存在的数据，或询问用户结果；不额外发一封催办邮件。
- 用户可报告“完成／部分完成／未完成／无法判断”，补充原因；不要求填写隐私正文。
- AI 观察可纠正、否定、删除；明确目标只能由用户创建／确认／修改。
- 关闭自动复盘不删除资料；单独提供清除记忆、清除复盘历史与导出。

### 3.4 连续复盘示例（合成情景，不是用户实际数据）

- 第一周：用户目标是规律学习，系统发现若干较大任务没有启动，只提出一个“小任务启动实验”，标记 PROPOSED，不认定用户已接受。
- 用户采纳并调整为“晚饭后先做一个小练习”；系统记录该行动的稳定 ID、用户修订与检查日，不自动创建待办。
- 后续日报：如只有学习总时长而没有启动次数，明确缺少验证该实验的指标，不根据时长增加就宣称实验成功；必要时请求一次用户反馈。
- 第二周：用户反馈更容易开始，但晚间时间不稳定。周报回看相同行动，提出调整触发时机，而不是重复要求更自律。
- 月报：回顾该实验的反馈与可比较指标，说明支持与不足；建议继续／调整／停止由用户决定。没有采纳、没有反馈或数据不足均不算失败。

## 4. 授权设计：实施前必须更新契约，不能绕过现有规则

当前 `server-network/AGENTS.md` 明确要求含财务数据的 AI 分析逐次确认。本方案提出一个**仅针对自动报告复盘的新授权类型**，不是把聊天／Slash Command 的逐次确认改成长期同意。用户选择“自动模式”只是产品方向，不等于已经认可具体供应商、范围与保存期限。

实施前需用户认可此设计，并同步适用 AGENTS.md；本次不修改现行规则。

### 4.1 授权内容

建议 `ReviewGrant` 至少保存：owner、grantId、revision、policyVersion、状态、授予／撤销时间、可选到期时间、周期、数据域、最大回溯天数、Provider ID、模型名、protocol、规范化 endpoint 指纹、最大调用预算、保留策略。指纹不含 API Key，设置响应不泄露密钥。

首版推荐允许：收支／资产／待办／学习的统计摘要、去备注的大额排行、历史复盘、用户确认的目标与反馈。不得仅因业务报告展示了订单备注，就把备注透传到模型。

- 供应商、endpoint、模型、协议、数据范围扩大、最长历史窗口或授权条款变化，必须重新确认；仅缩小范围可立即生效。
- API Key 轮换不改变数据接收方时不要求重授权，但重新校验连接；模型不可用不能静默切到另一供应商。
- 每次领取、实际模型请求前、结果保存前都检查当前授权 revision。已冻结待发 AI 邮件在领取前也检查授权及隐私处置标记。
- 撤销后取消未发请求，尽力取消进行中请求并丢弃其结果，未发送邮件改用另存的基础报告副本；不能撤回已提交给模型或邮箱的内容。
- 首版不调用外部 embedding／重排服务。将来增加这些接收方也需要新的明确授权。

### 4.2 隔离与审计

所有查询带当前用户，计划任务仅使用持久化 owner，不接受前端传入 ownerId。授权审计只记录范围、接收方身份、状态和时间，不记录密钥、完整提示词或财务正文。默认单用户部署不等于可以省略所有权检查。

## 5. 总体架构与小 Interface

```text
现有自动任务到期
  → 生成并冻结基础报告、类型化统计、口径与数据完整性
  → 短事务：保存执行 + 评审工作项 + 邮件等待记录
  → 现有任务调度／桌面提醒继续运行

独立评审 Worker
  → 原子领取工作项，检查授权与预算
  → 领域 Service 取历史事实，检索相关目标／观察／建议
  → ConversationContextAssembler 统一筛选、去重、裁剪
  → 规则选择主题 + 方法卡
  → 独立模型实例生成结构化草案（网络在事务／领域锁外）
  → 确定性校验／淘汰无证据内容
  → CAS 终态：保存结果与候选观察，冻结最终投递副本
  → 现有邮件 Worker 领取最终副本，沿用 SMTP 与失败语义

用户反馈
  → 记录采纳与结果、纠正记忆
  → 下一周期读取同一个建议 ID，调整建议而非重复建议
```

### 5.1 Module 归属

| Module | 归属与职责 | 对外 Interface（候选，非现有代码） |
| --- | --- | --- |
| ReportReview | `server-network/review/`；授权、事实、历史检索、反馈、工作项与最终结果 | `schedule(runId)`、`get(reviewId)`、`feedback(id, revision, decision)`；隐藏检索与状态机 |
| ReviewGeneration | `server-agents/review/`；无业务库依赖的结构化模型生成 | `generate(ReviewGenerationRequest) → ReviewDraft`，接受已最小化数据与取消／期限 |
| PersonalContext | 现有 `server-agents/context/`；唯一上下文 seam | 扩展 `assemble` 的用途／来源策略与有界候选输入，不开放任意路径／SQL |
| Report delivery | `server-network/automation/`；基础生成、投递等待、最终邮件领取与重发 | 通过 ReportReview 的小 Interface 调用，不了解记忆表结构 |

`server-network` 向 `server-agents` 提交中立数据契约；后者不能依赖 network DTO、Repository 或 Controller。业务 Repository 不作为上下文插件暴露给模型。生产模型 Adapter 与测试 fake 满足相同生成 Interface；首版不为未来 Mem0 先加多层空 Adapter。

### 5.2 统一上下文但不混入聊天记忆

当前 assembler 默认读取画像和工作区 MEMORY；首版复盘不自动继承这些来源。需显式增加 `useCase=REPORT_REVIEW` 和允许来源策略，只读取已授权的 review goals／observations／feedback。`CHAT` 路径保持现有默认行为、850 预算、暂停与空画像语义。

复盘候选由 network 经公开 Service 获取，作为带稳定 ID、来源、时间、类型和权限标签的只读数据输入；assembler 统一过滤与预算，不能为 REPORT_REVIEW 先加载整份聊天 MEMORY。复盘授权不能被聊天画像开关隐式打开；复盘暂停也不能删除聊天记忆。

事实报表属于当前任务证据，不当作个人画像；个人目标和历史召回合计仍限制在 850 个估算 Token（目标／约束最多 300，召回最多 500，预留包装余量）。如需要扩大，先通过用量评测和 DOX 审核，不在调用方偷偷提高上限。

## 6. 事实与记忆模型

### 6.1 四层记忆

| 层 | 示例 | 写入与信任规则 |
| --- | --- | --- |
| FACT | 9 月学习时长、某币种支出、窗口覆盖天数 | 程序从领域 Service 计算；模型不能改数值 |
| USER_CONFIRMED | 想每周完成一篇学习输出；不接受牺牲休息 | 用户显式输入／确认，保留 revision 和有效期 |
| AI_OBSERVATION | “任务拆分后，启动次数可能增加” | 自动保存为带证据的候选或不确定观察，不升级为用户事实 |
| ACTION_FEEDBACK | 建议内容、采纳、检查日和结果 | 模型只能提出；采用与主观结果由用户提交；客观指标变化另列 |

不把“少记了几笔”“没反馈”“任务未完成”自动归因为懒惰、焦虑或不自律。模型 confidence 是自报不确定性，不是统计概率或经过校准的真值。

### 6.2 持久化建议

业务数据保存在现有 `~/.butvan-agent/data/butvan.db`，仅通过新的 Flyway 迁移新增正式领域表；不写 localStorage，不另建 `.agentscope` 运行态数据库。建议表名与字段在实现评审时最终确定：

| 候选表 | 核心正式字段与约束 |
| --- | --- |
| `review_settings` / `review_grant` | owner、开关、周期、预算、model identity、grant revision、到期／撤销；密钥只引用配置 |
| `review_fact_snapshot` | owner、业务域、周期／时区、cutoff、coverage、来源指纹、metricKey、currency、金额分值／计数、版本；同来源不重复累计 |
| `review_goal` | owner、目标、约束、衡量方式、状态、revision、有效期；用户维护 |
| `review_job` / `review_result` | reviewId、业务去重键、输入指纹、状态、attempt、lease token、deadline、grant／goal／策略版本、模型信息、结构化结果、usage 引用 |
| `review_observation` / `review_evidence` | 类型、topicKey、来源事实／反馈 ID、反证、时间范围、可信状态、过期、supersedes、revision；证据正式关联，不只藏在 JSON |
| `review_action` / `review_feedback` | 稳定 actionId、goalId、动作、topicKey、检查日、提议／采纳状态、结果、来源复盘、revision；采纳不等于完成 |
| `automation_review_delivery` | owner、runId 唯一、reviewId、等待期限、基础副本、最终文本／HTML、冻结时间、选定投递副本 |

结果 JSON 只保存不可变的版本化生成结构，不能替代可查询的状态、所有权、金额、时间与外键列。金额按分及币种存储，不把 renderer 的字符串 Metric 当领域事实模型。

原有执行记录、基础报告和最终评审分别保留来源，普通关闭／升级／重发不改旧快照。任务清空、复盘清空与删除引用必须通过领域 Interface 联动，不让复盘外键阻断现有任务回收站。删掉一个任务不等于删掉用户所有跨任务复盘；删除来源后记忆标记无证据／失效，不保留可继续引用的悬空事实。

### 6.3 首次运行与历史修订

- 不从“最近 50 封邮件”的 HTML 提取历史。通过日历、学习、财务公开 Service 按自然周期读取所授权窗口。
- 首次最多回看 180 天、按批计算，建议批次最多 7 个日分片；无模型调用。摘要不足以在期限内完成时先用已有窗口生成，标明不足，不能拖延邮件。
- 后续只补新窗口与失效窗口；数据变更事件在事务提交后标记相关摘要待重建，并在正式评审前校验来源版本／指纹。未知变更范围时保守失效，不做“只靠累计计数”的永久真相。
- 记录 sourceAsOf 和 metricVersion，区分“当时生成的事实快照”与“今天账本重新计算的历史”；旧邮件不随补录改写，新评审要说明重大修订。
- 日报当天截至生成时属于未闭合窗口；不能当作完整一天和完整前日直接推断效率下降。月长、时区、缺失天数、币种和周期待办去重均在程序端处理。需要时间截断的领域查询若目前仅支持 LocalDate，P1 应扩展领域只读 Service 的 cutoff 能力，不能在复盘模块绕过 Service 拼 SQL，也不能让基础报告与 AI 证据采用互相冲突的统计口径。
- 新增账户、划账、校准、已入账收益与未知删除档案，遵守现有财务口径。没有历史余额证据时只说明无法判断。

## 7. 检索、去重与长期跟进

1. 先过滤 owner、授权域、有效时间、删除／被纠正记录、来源完整性。
2. 必选当前有效目标和到期待检查行动，再从相关观察中选择；总量仍受 850 Token 限制，不能无界塞入所有待办建议。
3. 首版按 topicKey、时间范围、目标关联、支持／反对证据和最近反馈排序；采用确定性标签／时间检索，不引入 embedding 成本。
4. 相关性高不代表正确：被否定、过期或来源被删的观察不可作为支持证据；同一原始事实被日报／周报引用仍只算一个支持来源。
5. 采用同一个 actionId 进行跟进。未采纳建议不评价执行成败；未反馈状态保持 UNKNOWN。
6. 建议默认冷却 7 天；同 topicKey 的未处理行动优先跟进，不再开新建议。拒绝时可选“30 天内不再建议”，用户可解除。
7. 日／周／月同一时段生成时，按 owner 串行领取评审；先生成月、再周、再日，让短周期看到已提出的建议。仅影响同一批排队，不为了等未来报告延迟当天邮件。
8. 重复任务相同周期／范围／模型／授权版本可共用一次评审；不同范围不得共用结果。不同任务的邮件投递仍各自独立。

## 8. 生成与质量控制

### 8.1 先规则取证，再模型解释

程序生成 evidence registry：`factId、metricKey、period、value、unit、currency、coverage、sourceAsOf、qualityFlags`。程序计算差额、比例、日均和可比较性，模型不自行算账。

候选主题先过规则：历史样本至少 3 个完整可比窗口才允许描述“重复趋势”，不足时只做当期观察；阈值作为版本化产品启发式，不能称为统计显著。大额收支、学习增加本身不是负面，必须结合用户目标与约束。

模型无工具、无 shell、无浏览器权限，不可修改业务数据；备注／标题／用户输入作为不可信数据，不能成为系统指令。基础报告中的自由文本默认不进入模型，必须保留的目标文本使用长度限制和独立数据块。

### 8.2 结构化输出契约（草案）

```json
{
  "schemaVersion": 1,
  "coverageNote": "可用数据范围与限制",
  "observations": [{
    "topicKey": "study.start-friction",
    "kind": "FACT_OBSERVATION|HYPOTHESIS",
    "text": "不带未经核实数字的简洁观察",
    "evidenceIds": ["fact-..."],
    "counterEvidenceIds": [],
    "uncertainty": "哪些还无法确认"
  }],
  "followUps": [{"actionId": "已有行动 ID", "text": "新证据，不擅自判定已完成", "evidenceIds": ["fact-..."]}],
  "actions": [{
    "topicKey": "study.start-friction",
    "goalId": null,
    "methodId": "small-start-v1",
    "text": "一个足够小的动作",
    "rationale": "为什么可能适合",
    "evidenceIds": ["fact-..."],
    "checkAfterDays": 7,
    "successCriterion": "怎样检查是否有帮助"
  }],
  "observationProposals": []
}
```

服务端生成 actionId，不接受模型为新行动指定任意旧 ID；methodId、factId、goalId 和 followUp actionId 必须属于本次白名单。

### 8.3 校验与降级

- 校验 schema、未知字段、数组长度、引用归属／权限／版本、期限、禁用目标、方法适用条件与输出长度。
- 数字展示由 renderer 根据 evidenceIds 取值；模型正文出现事实性金额／百分比必须能对应 registry，否则丢弃该项。未来动作中的“5 分钟”等目标数字与事实数字区分处理。
- 缺依据、反证被忽略、与约束冲突、重复建议、心理诊断、投资结论的内容不进入邮件。
- 校验通过只能证明格式与已知约束，不保证文字推理正确。针对因果过度推断保留回归样例和人工评测，不声称靠数字扫描就能解决所有幻觉。
- 首版最多一次模型生成，不让另一个模型凭同意意见“证明”建议可靠，不自动循环修复。
- 剩余内容可独立成立则局部保留；不能成立则降级为“本次 AI 复盘未生成，数据报告正常”。基础报告 PARTIAL 与 AI 降级是独立状态。

### 8.4 方法卡，而非书籍全文 RAG

首版自写 4–6 张短方法卡：小步启动、减少环境阻力、目标与投入对齐、区分决策与结果、一次只改一个变量、检查恢复与留白。每张卡有 methodId／版本、来源链接、适用条件、反例、问题与实验步骤。

方法卡为静态资源，按主题最多选择 2 张。引用思想并自行表达，不复制书籍大段内容、不导入未授权整本书。用户无精力或高压力不等于需要更强刺激，卡片不能成为强行要求每天进步的工具。

## 9. 状态机、并发、费用与异常恢复

### 9.1 评审状态与幂等

```text
PENDING → RUNNING → SUCCEEDED / DEGRADED
PENDING / RUNNING → SKIPPED（未授权／撤销／超预算／过期）
RUNNING → UNKNOWN（提交后超时或进程中断，无法确认供应商是否已执行）
```

同 owner、周期类型、周期起止、时区、数据域指纹、goal revision、grant revision、模型连接指纹、生成策略版本构成复盘去重键；输入数据指纹单独保存。同一周期的数据补录不自动产生新付费评审，默认复用原结果；用户主动“重新评审”必须显式确认新调用并产生新版本，不回写已冻结邮件。

工作项通过短事务 CAS 领取并取得 fencing token；完成时匹配 job revision、token、授权 revision 和 deadline，迟到 Worker 不能覆盖终态。另需按 owner 的数据库执行槽位／带 fencing 的租约，防止两个 Worker 领取同一用户的不同 job 后并行生成；只做 job 级 CAS 不足以实现用户串行。内存 synchronized 不是唯一保护；需数据库唯一约束与条件更新。

网络提交后崩溃无法保证供应商只收费一次。首版不自动重试 UNKNOWN／模型生成失败，不因 lease 过期盲目重发；改发基础报告。仅请求尚未发出或有确切未执行证据的阶段可安全恢复。用户显式重评须说明可能重复收费。

### 9.2 邮件的两段式冻结

现有 TaskRun 基础内容不被异步 AI 静默覆盖。新增 delivery 记录：

1. 基础快照创建后，AI 开启的执行设为等待最终邮件副本；邮件 Worker 不得提前发送。
2. AI 成功或期限到达后，短事务中一次性冻结 `finalText/finalHtml`，并从此时设置实际入队时间。AI 未完成时选择基础副本并注明原因。
3. 新邮件领取、历史展示与重发都通过同一个 resolved delivery Interface 读取选定副本；旧 run 没有 delivery 记录时兼容原 content/emailHtml。
4. 结果晚到不能补发第二封邮件，也不能升级已经发出的基础副本。
5. SMTP 的 UNKNOWN 继续沿用现有人工重发确认，不与模型 UNKNOWN 混为一谈。
6. 同一 review 被多个任务共用时，每个 delivery 独立冻结；已经冻结的副本不因新目标或新评审改变。

授权撤销／用户清除记录是显式隐私操作：对未投递 AI 副本设置禁用标记，只能选择已冻结的基础副本或取消投递，不偷偷重写旧 AI 原文。已经投递的邮件不可能撤回；用户明确清除历史时可删除本地内容并保留最小去重 tombstone，重发入口必须同时失效，不能为满足快照不变而拒绝隐私删除。

### 9.3 建议默认资源上限（待实测校准）

| 项目 | 日报 | 周报 | 月报 |
| --- | --- | --- | --- |
| 模型请求次数 | 1 | 1 | 1 |
| 总输入 Token 硬上限 | 5,000 | 6,500 | 8,000 |
| 输出 Token 硬上限 | 600 | 1,200 | 1,800 |
| 单次模型请求期限（含网络读取） | 15 秒 | 25 秒 | 40 秒 |
| 排队到最终邮件冻结总期限 | 90 秒 | 120 秒 | 150 秒 |
| 用户目标＋召回内容 | 各周期合计最多 850 Token；默认 Top-K 4，不足预算进一步裁剪 | 同左 | 同左 |

System prompt 不超过 1,200 个本地估算 Token；总输入预算还必须包含事实、方法卡、JSON 信封与消息包装，不能只截断历史。超限先减少背景窗口与低相关片段，不截掉来源／单位后继续做判断；仍超限则降级。

每用户最多一个进行中的模型调用；全局有界队列，建议待处理最多 100 项，满时直接基础报告，不无限积压。截止时间覆盖排队，队列等待已耗尽时不得再启动模型。单请求期限与总期限分开设置：同日月／周／日顺序的模型耗时上限合计约 80 秒，不能让默认的 30 秒排队期限导致日报必然在月报之后过期；仍需为事实收集和验证留余量，最终由 deadline 降级保证有界等待。

默认每用户每天最多 3 次自动付费生成，重复任务优先复用；领取时在事务中原子预占当日调用额度，明确未提交供应商的请求才释放，UNKNOWN 仍占用，避免并发或崩溃突破上限。用户可在明确费用提示后调高。日报与周／月同日达到上限时优先月、周、日。此处是调用上限，不是准确货币上限；只有维护相应模型价格且覆盖缓存／额外计费项后，才能展示可信金额预算。供应商未上报 usage 时记录未知，不伪造实际 Token。

取消要传播到响应订阅、HTTP 请求与工作线程；供应商不支持取消时仍用 CAS 拒绝迟到结果，并保留可能已收费的提示。业务线程、原自动任务两个 Worker 均不等待模型。

## 10. 前端与后端 Interface 规划

以下为拟新增路径，统一 `Result<T>` 包装、`@ApiLog`、当前用户解析；不把持久化对象或第三方模型对象直接返回。日志参数需脱敏，不能由 ApiLog 意外记录目标／反馈正文。

| 方法与路径 | 输入／响应要点 | 权限与错误语义 |
| --- | --- | --- |
| `GET /agent/reviews/settings` | 脱敏设置、授权状态、revision、模型身份与预算 | 当前用户；不返回 Key |
| `PUT /agent/reviews/settings` | expectedRevision、周期、上限、model ref；返回新 revision | 冲突拒绝覆盖；扩大范围需新授权，保存设置不等于授予 |
| `POST /agent/reviews/grants` | expectedRevision、policyVersion、明确的数据与模型范围 | 只允许显式确认；记录授权，不顺带调用模型 |
| `POST /agent/reviews/grants/{id}/revoke` | expectedRevision；返回撤销状态 | 原子撤销并使待处理工作失效 |
| `GET/POST /agent/reviews/goals`，`PUT /agent/reviews/goals/{id}` | 目标、约束、衡量方式、revision；分页列表 | 仅当前用户；正文长度与乐观锁校验 |
| `GET /agent/reviews?cursor=&limit=`，`GET /agent/reviews/{id}` | 有界历史、事实依据、AI 状态与反馈；limit 默认 20，最大 50 | 不能读取其他 owner；历史详情不触发生成 |
| `POST /agent/reviews/actions/{id}/feedback` | requestId、expectedRevision、采用／拒绝／结果／修订 | 请求幂等；不能跳过“采纳”自动当作已执行 |
| `POST /agent/reviews/observations/{id}/correction` | requestId、expectedRevision、否定／纠正 | 来源链失效；不自动改画像 |
| `POST /agent/reviews/preview` | 已保存 taskId、requestId、明确 AI 请求；202 型任务受理结果 | 会产生成本；授权有效且有预算；临时结果不写长期建议 |
| `GET /agent/reviews/previews/{id}` | 临时任务状态与结果；15 分钟过期 | 只读当前用户；不得重触发模型；首版由 SSE 提示完成后读取 |
| `POST /agent/reviews/{id}/regenerate` | requestId、expectedRevision、acceptPotentialDuplicateCharge | 明确付费重评；新版本不修改已发邮件 |
| `GET /agent/reviews/export`，`POST /agent/reviews/erase` | 导出；擦除范围、expectedRevision、明确确认 | 清除前撤销相关工作，清除不是暂停；导出不得含 Key |

异步“202 型受理”指返回 job/status，不预设现有全站 HTTP 风格已支持 202。实现时明确 HTTP 状态与 Result.code 映射，不顺带修改全站错误处理：至少区分参数非法、无权／未授权、资源不存在、版本冲突、预算不足、模型不可用、任务过期；前端统一中文错误映射。

复盘进度复用任务 SSE 的后端权威快照／历史失效提示，首次连接及重连可恢复；不新增定时 HTTP 轮询。大段结果按需读取，不把全部记忆塞进每个任务快照。

新增候选 UI：`ReviewSettings`、`ReviewHistory`、`ReviewEvidence`、`ReviewFeedback`，配套 CSS Modules；复用 SettingsGroup、SettingsRow、Message 与现有基础组件。实施时同步根 `UI COMPONENTS.md`，本次未新增真实组件，无需虚构清单记录。

| P0：范围与契约 | 确认本方案决策项、补充自动授权的 DOX 契约、冻结 DTO／来源策略 | 未确认授权前，不能把含财务数据的自动模型调用做成可启用功能 |
| P1：事实与授权 | 数据迁移、授权／配置、类型化事实与有界历史初始化、固定测试样本 | 无模型也能检索正确历史；币种、缺失、补录、owner 隔离测试通过 |
| P2：记忆闭环 | 目标、候选观察、建议／反馈、纠正／遗忘、跨周期去重 | 记得上次行动，但不把未反馈算失败；被纠正内容不再作为证据 |
| P3：生成与质量 | 独立模型实例、有界上下文、方法卡、JSON 校验、Token／用途归因 | fake 模型与离线基准通过；生产模型试验须单独授权，CI 不发真实隐私数据 |
| P4：自动执行与邮件 | Worker、领取／期限、两段式冻结、崩溃恢复、基础报告降级 | 不阻塞现有调度；重复领取／迟到／重发不重复生成或改变旧邮件 |
| P5：前端与试用 | 设置、授权说明、证据／反馈、SSE、导出清除、产品说明与 UI 契约 | 默认关闭；从开启到收信、纠正、撤销、清除的自动化场景可验证 |

P1–P3 可用 fake 和显式 AI 预览验证，最终交付仍以用户选择的自动模式为主，不把手动版本当最终结果。整个首版包含 P0–P5；不能只做邮件点评后把长期反馈无限延期。

不在本次文档任务中创建分支／合并／推送。后续代码功能分支按仓库策略从 main 创建，需要用户明确授权；不要把当前报告样式分支直接当作所有后续新功能的默认分支。

## 13. 测试与效果评测

### 13.1 自动化验收

- 事实：跨月／闰年／时区、部分日报、不同月长、多币种、不适用完成率、重复周期待办、转账／校准／新账户、未知历史档案。
- 历史：180 天上限、分页与批次、补录后失效、同源跨周期不重复计数、无记录与不可用区分。
- 记忆：目标 revision、用户否定、过期、来源删除、反证、采纳但未知结果、跨用户隔离、清除后不复活。
- 权限：默认关闭、范围扩大重授权、固定接收方、模型切换不静默降级、运行中撤销、待发 AI 副本禁用。
- 模型：无工具调用、提示注入样例、非法引用／数字／JSON、过长输出、结构化模型不支持、超时／取消、usage 未上报、Token 硬上限。
- 并发：双 Worker、跨任务共享、同周期多次点击、过期 lease fencing、队列满、重启提交不明、迟到结果丢弃、邮件 UNKNOWN 独立处理。
- 兼容：旧任务默认不调用 AI、旧 run 原样重发、冻结后的反馈不改邮件、普通预览无模型／记忆副作用、久坐和提醒时序不被阻塞。
- UI：服务层类型、TypeScript／构建／相关自动化测试；不默认截图或逐页手工浏览。

### 13.2 建议质量的离线基准

准备至少 30 组匿名或合成的多周期案例，覆盖冷启动、无明确目标、目标冲突、数据不足、假相关、既往拒绝、已有行动、正面进步、收支异常但合理等。每例列出期望事实、禁用结论、允许行动，不以措辞与参考答案完全一致为标准。

上线门槛：自动样例中引用越权、已知虚假数字、把未知反馈判失败、绕过撤销均为 0；基础报告可靠降级用例全部通过。对“依据充分／符合约束／行动具体／不重复／不羞辱”做人工评分，建议至少 80% 案例全部达到可接受，且无严重有害建议；这是产品验收阈值，不是模型普遍正确率承诺。

生产试用后观察用户纠正、拒绝原因、重复建议和建议采纳后的自报效果。采纳率不能单独作为优化目标，否则会鼓励讨好；趋势改善也不证明是 AI 建议造成。

## 14. 数据保留、费用与运行风险

建议默认：事实摘要、评审及观察最长 180 天；用户明确目标与已采纳行动保留到归档／用户删除；候选观察 30 天过期，未被重新支持即不再召回。保留期限单独设置，延长需要说明范围。过期后删除派生索引和可恢复内容，只留不含正文的必要去重信息；不能靠向量库“删除了索引”冒充删完数据。该保留策略也覆盖含 AI 正文的本地最终投递副本及预览缓存，清理后相关 AI 邮件不可重发，不能一边删除记忆一边无限保留相同正文的副本。基础报告沿用自动任务原有保留规则；已经发送到用户邮箱的副本与用户自行导出的文件不能由本系统删除。

完整提示词不另落日志；为复盘保留必要最小证据与 revision，不复制整份业务数据。系统 usage 继续以 `~/.butvan-agent/usage/system-usage.jsonl` 为权威，不能把实际 usage 只写 SQLite；调用关联信息不包含正文，删除复盘正文不应删除用户全局账单。需为系统用量记录增加可选 reviewId／jobId 关联和版本化本地归因：报告事实为 RAG、用户目标为 Profile、历史召回为 Memory Recall；实际 usage 与这些估算分开保存。现有 SystemUsageLedger 尚未提供全部关联与归因字段，P3 要同步扩展可重建读模型和兼容旧 JSONL，不能只在复盘表单独维护一份实际总量。导出要包含 schemaVersion、来源范围及授权记录，不包含凭据。

SQLite 本身不宣称加密；本机与服务器需受保护的数据目录、备份和访问控制。远程模式的授权与工作项留在远程后端；本机退出不影响在线远程调度，本机模式进程退出则暂停。切换后端不自动复制财务授权或重复执行原计划；跨后端高可用调度不是本版承诺。

| 风险 | 处理 |
| --- | --- |
| AI 反复强化自己的错误判断 | 推测不升格为事实，必须引用原始证据；纠正链与过期；不靠重复自述提高置信度 |
| 历史摘要和回溯不是不可变真实历史 | 保存 sourceAsOf／版本，标注已知限制；新数据可修订，旧邮件不改 |
| 多周期建议互相矛盾 | owner 串行、同 actionId 跟进、目标／约束优先、近建议去重 |
| 网络断开但供应商已收费 | UNKNOWN，不自动重试；基本报告继续，显式重评提示费用 |
| 评审造成提醒阻塞或超时发两封 | 独立执行器、deadline、CAS 冻结、邮件等待门禁、迟到不补发 |
| 读到了模型未授权的敏感内容 | 类型化最小化、来源白名单、不能透传基础报告备注或聊天 MEMORY |

## 15. 待用户确认的决策与推荐默认值

1. **自动授权范围**：推荐统计摘要＋历史复盘＋用户确认目标／反馈，不含完整流水备注、聊天或资料正文。需要实际授权页面确认后才能启用。
2. **模型**：推荐用户选择一个现有模型连接固定使用，不自动跟随聊天模型切换；具体模型需用户指定，方案不替用户选供应商。
3. **费用与频率**：推荐每天最多 3 次自动生成、每期一次、失败不自动重试；Token 与期限按第 9 节。若有多套报告任务须说明上限可能导致部分邮件只带基础报告。
4. **语气与方法**：推荐温和直接、重证据不打分；先从 4–6 张有出处的方法卡开始，不导入整书。
5. **保留与窗口**：推荐最多回看／保留 180 天，明确目标和已采纳行动由用户归档／删除；候选观察 30 天过期。

上述为可讨论默认值，不把“先给方案”解释为对所有数据范围、费用或持久化策略的批准。
