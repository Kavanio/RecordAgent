# RecordAgent iOS 工程约束

本文件适用于当前目录及全部子目录，叠加仓库根目录 `AGENTS.md`。每次修改前读取两者；涉及产品范围、接口或数据归属时，另读 [开发前规划.md](开发前规划.md)；涉及多语言设计与文案约束时，另读 [国际化规范.md](国际化规范.md)；处理桌面历史数据迁移时，另读 [桌面历史数据迁移-后续事项.md](桌面历史数据迁移-后续事项.md)。本文是 iOS 工程的强制工作契约。

## 一、范围与技术基线

- 使用 Swift、SwiftUI、Xcode 开发原生 iOS App。首版交付邮箱注册/登录、首页、设置和完整桌面日历能力；底部常驻首页、日历、工作台、我的四个入口，工作台集中进入财务、资料、记录和任务。财务、资料、记录（桌面端学习与专注记录）先展示当日投影，完整业务与任务（桌面端自动任务）后续逐步实现。Agent、聊天、模型和桌面运行时不进入本工程。
- 业务数据由未来部署的多用户后端通过 HTTPS API 提供；桌面端与 iOS 最终访问同一服务和同一用户数据。服务端负责业务校验和持久化，iOS 负责交互、展示、输入预检和设备能力，不直接访问后端数据库。
- 开工时在 Xcode 工程中锁定最低 iOS 版本、Swift 语言版本、Bundle ID 和构建配置；新增依赖须记录用途、维护状态、许可证和替代方案，优先使用系统框架。
- 当前阶段先实现 iOS 界面、状态与 API 请求层；以可控假服务验证完整流程。真实多用户服务端、桌面端切换和历史数据迁移分别按后续阶段推进，不让未部署的服务阻断客户端结构与交互开发。

## 二、目录与依赖方向

创建工程时采用以下职责结构；仅在确有独立职责时新增目录，不建立无边界的 `Utils/`、`Helpers/` 或 `Common/` 大杂烩。

| 路径 | 职责 |
| --- | --- |
| `RecordAgent/App/` | App 入口、依赖组装、根导航与环境配置。 |
| `RecordAgent/Features/<Feature>/` | 每个业务功能的 View、展示状态、交互协调；功能内按需再分子目录。 |
| `RecordAgent/Domain/` | 跨功能共享的业务类型、纯规则和协议；特定功能的类型留在对应 Feature。 |
| `RecordAgent/Services/` | API 客户端、鉴权、DTO 映射、附件传输、Keychain 与系统能力适配。 |
| `RecordAgent/DesignSystem/` | 复用控件、视觉令牌、排版与交互样式。 |
| `RecordAgent/Resources/` | 本地化、图片、字体及不含密钥的静态资源。 |
| `RecordAgentTests/`、`RecordAgentUITests/` | 领域/API 测试与关键用户流程 UI 测试；创建工程时同步建立。 |

- 依赖方向为 `App → Features → Domain`，`App` 组装 `Services` 实现。Feature 通过协议使用 Services；Domain 不依赖 SwiftUI、网络库或持久化实现。跨 Feature 复用先明确领域归属，再提取共享类型或组件。
- 一个文件保持一个主要职责；视图负责渲染和事件转发，状态对象负责异步加载及操作状态，服务负责请求和 DTO 映射。视图中不拼 URL、不直接调用 `URLSession`、不解析服务端 JSON。
- 与桌面端共享的是业务语义和 API 契约，不复制 React/Tauri 组件或 Java Service。新增或修改接口时同步更新后端 DTO、iOS DTO/映射及接口文档。

## 三、Swift 代码规范

- 类型、协议、枚举用 `UpperCamelCase`；方法、变量、属性、枚举成员用 `lowerCamelCase`。命名表达业务含义，避免无意义缩写和 `Manager`、`Helper` 等模糊职责名。
- 默认使用最小可见性：实现细节设为 `private`，仅跨文件需要的声明保持 `internal`，确有模块公开需求再使用 `public`。优先用 `struct` 表达值；需要共享身份或生命周期时才用 `class`。
- 对外接口、非显然业务规则和复杂分支写准确中文注释，说明约束与原因；简单代码靠命名表达。删除过时注释，不保留被注释掉的旧实现。
- 使用 Swift Concurrency 的 `async/await` 和结构化任务；UI 状态更新在 `MainActor`，取消时传播取消，不在 `View.body` 发请求。异步操作明确加载、成功、空、失败与重试状态，避免重复提交。
- 用明确的错误类型处理网络、鉴权、校验、冲突、离线和服务端故障。禁止 `try!`、强制解包外部数据或静默 `catch`；用户只看到可理解的中文错误，日志保留排障上下文但不含敏感内容。
- 避免 `Any`、魔法字符串和重复的日期/金额转换；用类型化 DTO、枚举与集中映射。金额按最小货币单位整数传输，日期、时间、IANA 时区分别表达；更新按 API 要求携带版本号。
- SwiftUI 组件提供清晰的输入和事件边界、稳定标识及无障碍标签。重复交互抽成共用组件；布局适配动态字体、安全区域、深浅色和常见屏宽。**多语言与文案规范**：全面采用 iOS 17 String Catalogs（`Localizable.xcstrings`），控件对外接口优先使用 `LocalizedStringKey`，动态文本使用参数化插值；禁止在视图层硬编码中英文字符串；日期、时间使用环境感知格式化；UI 容器避免定死宽度以适配英文自适应拉伸。
- **全面屏与 LaunchScreen 强制约束**：必须在 `project.yml` 与 `Info.plist` 中保持 `UILaunchScreen: {}` 字典配置；严禁遗漏或在重构时删除启动屏幕声明，以杜绝 iOS 系统因缺少现代启动屏而降级回落为旧分辨率兼容模式，导致真机上下出现巨大黑色留白（Letterboxing）。
- **SafeArea 与全屏响应式布局**：所有页面的底色与背景渐变必须使用 `.ignoresSafeArea()` 铺满整个屏幕；主内容在 SafeArea 内通过弹性容器和滚动视图（`ScrollView`）承载，禁止写死屏幕高宽，确保小型屏至 Pro Max 均能自适应流动且无黑边、无遮挡。自定义底部导航栏（TabBar）必须采用 `.safeAreaInset(edge: .bottom)` 或通过 `.ignoresSafeArea(edges: .bottom)` 将背景贯穿延伸至物理屏幕底部，避免导航栏底端因未铺满 SafeArea 而悬空留白。
- **构建配置一致性**：`project.yml` 是 Xcode 工程配置的单一事实来源，任何针对 `Info.plist`（如 `UILaunchScreen`、`UISupportedInterfaceOrientations`）、多语言区域声明（`knownRegions`、`defaultLanguage`）或编译参数的改动必须同步在 `project.yml` 中登记，杜绝 `xcodegen generate` 后配置丢失。


## 四、首页与导航契约

- 首页保留顶部问候与轻量插画，中间用统一画布、留白和低饱和色展示选中日期的待办、财务、资料、学习专注记录；四类摘要和近七日趋势不添加卡片外框、分割线或悬浮添加按钮。默认日览以横向分页展示四类内容摘要，进入单一分类后再展示完整条目，不将全部类别混排为列表。
- 周历使用原生横向分页滚动，滑动停稳后再提交新日期，切周保留星期位置；程序化切月不得误触发滑动回选。月份入口提供年份与月份选择，切月时将不存在的月末日收敛到目标月最后一天。所有自然日计算集中在 `Domain/Home/HomeModels.swift` 的 `HomeCalendar`，不使用固定秒数跨日。
- 四个底部入口始终存在且等宽；激活态只改变图标与文字的前景色、字重，不添加选中背景；页面切换响应系统“减少动态效果”。工作台列出财务、资料、记录、任务四个入口，各业务页可返回工作台；`MainTabView` 持有按日状态，切换业务入口保留选中日期。首页与日历共享筛选，独立业务预览按所属分类显示数据；任务入口不得复用日历待办。
- 首页按日数据经 `HomeDataServiceProtocol` 读取和写入，由 `AppEnvironment` 装配。Debug 使用按日隔离、明确标注的会话内示例服务；Release 在真实 API 未接入前展示不可用状态，不展示假数据。日期或语言变化时重新加载，并隔离过期响应；金额使用整数分，图表使用快照派生的实际数值，默认显示财务支出并可通过轻量菜单切换专注记录；曲线连续过渡，触摸或指针悬停可查看日期和数值。Banner 图片边缘通过透明遮罩与页面背景融合，不叠加固定颜色盖片。
- 本次首页与导航动画响应系统“减少动态效果”；文本、日期、金额和分钟数跟随语言环境。`HomeTests` 覆盖月末、闰年、跨年、夏令时、日期隔离、示例状态回读与请求竞态。

## 五、API、数据与安全

- API 基础地址按 Debug/Release 环境集中配置，生产环境只使用 HTTPS；服务层统一处理超时、编码/解码、状态码、业务错误、鉴权失效和请求取消。接口响应不得直接当作 SwiftUI 状态模型使用。
- 接入真实服务器前必须完成多用户身份认证、每请求用户隔离与授权。现有 `CurrentUserProvider` 固定用户和桌面 `localhost:8081` 仅供当前单机工程使用，不能作为公网方案。
- 邮箱是登录标识；桌面端和 iOS 必须由服务端认证为同一个稳定用户 ID，才能读取同一份业务数据。当前桌面“邮箱绑定”只是本机账户资料，不得将其视为已具备跨设备登录能力。
- 注册时用户填写邮箱并设置密码，由服务端发送邮箱验证码，验证通过后创建账户。登录默认使用邮箱和密码，同时支持邮箱验证码登录；两种方式必须解析为同一个稳定用户 ID。会话更新和密码找回流程在账户接口设计时确定，不把桌面本地密码哈希或验证码状态当作服务器凭据。
- 当前阶段的假服务只能用于开发和测试，需与真实 API 实现分离；用户设备上的真实账户和业务数据必须通过受认证的服务端 API 处理。桌面历史数据未来归属当前邮箱账户，迁移步骤见后续事项文档。
- 访问令牌等秘密存入 Keychain；源码、构建配置、UserDefaults、日志和异常提示中不出现令牌、密码、财务明细或资料正文。系统权限在用户触发相关功能时按需申请。
- 服务端是业务数据权威。本地只保存明确设计的缓存、临时附件和凭据；缓存有失效与清理规则。离线写入、冲突合并、后台同步须先有单独设计及测试，再加入实现。
- 附件通过服务端文件 ID 关联，上传下载经过受控 API；临时文件清理、大小限制和失败反馈必须明确。日历待办、自动任务、学习记录和资料手记分别沿用后端现有领域事实，不建立同名的第二套数据。
- 后续实现自动任务时，沿用服务端任务配置、调度和执行记录；iPhone 系统通知是手机提醒渠道。通知投递、跨设备去重、权限与确认回执在任务阶段单独设计，不以客户端定时器代替服务端调度。

## 六、变更流程与验收

1. 修改前确认工作区状态、适用 `AGENTS.md`、目标功能现有实现和接口契约；保留用户已有改动。
2. 新功能先确定所属 Feature、输入输出、失败/空状态和测试边界；影响职责、目录、接口、权限或体验时同步更新规划文档与 DOX。
3. 对金额、周期日期、时区、版本冲突、鉴权失效、响应映射和附件边界编写有意义的测试。API 测试使用可控假服务；关键流程再用 UI 测试和真机验证。
4. 工程建立后，每次代码改动至少运行对应配置的格式/静态检查、Xcode 构建和受影响测试；无法执行时说明原因和未验证范围。提交前检查 diff、敏感数据与构建产物；仅提交本次范围，遵守根目录提交规则。

验收标准：目录归属与依赖方向清楚，API 和 UI 状态覆盖成功及主要失败路径，必要测试与构建通过，文档和实现一致，工作区无本次产生的秘密或构建产物。
