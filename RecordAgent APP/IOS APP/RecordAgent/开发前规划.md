# RecordAgent iOS 开发前规划

> 状态：方案草案（2026-09-23）。本文确定首版范围与建议技术栈；数据归属和“任务”含义仍需产品决策，决定后再创建 Xcode 工程。

## 1. 产品边界

RecordAgent 是面向 iPhone 的独立个人数据应用。首版包含日历、财务、资料、记录、任务五个入口，不包含聊天、模型、AgentScope、工具调用、记忆、Token 统计或桌面端运行时。界面与交互按触屏重新设计，不直接移植 React 页面。

| 入口 | 首版建议能力 | 现有项目依据 |
| --- | --- | --- |
| 日历 | 月视图、每日事项、日程和周期待办、手记投影 | `daily/` 的日记录服务及 `DailyEventController` |
| 财务 | 资产账户、手工收支、划账、余额校准、流水及月度统计 | `finance/` 的服务、DTO 和 Controller |
| 资料 | 分类、富文本正文、标签、附件、回收站 | `record/` 的服务、文件资产与 Controller |
| 记录 | **待确认含义**；候选是按日手记和历史回看，不新增独立数据事实 | 目前“资料”后端 `record/` 已含每日手记，并与日历双向投影 |
| 任务 | **待确认含义**；候选 A：日历待办，候选 B：桌面端自动任务 | 日历待办在 `daily/`；桌面自动任务在 `automation/`，`/api/tasks` 是 Agent 子任务 |

建议首版把“任务”定义为待办清单和提醒，复用日历待办数据；桌面自动任务涉及电脑状态、邮件、调度与执行回执，不能直接映射为 iPhone 本地提醒。若要纳入，须单列需求和服务端运行方案。资料与记录也应先确定是两个导航入口，还是一个入口的两种视图，避免双份数据。

## 2. 已确认的复用边界

- 可复用：现有领域规则、字段语义、业务测试案例和 API 契约作为设计输入。周期待办按自然日/周/月计完成，月待办落在月末；金额按最小货币单位整数存储；资料使用稳定 ID、版本号、软删除与附件 ID；每日手记在日历和资料间保持同一事实。
- 不能直接复用：React/Tauri 组件、CSS、Java Service 二进制或桌面 sidecar。现有数据保存在电脑的 `~/.butvan-agent/data/butvan.db` 和同级文件目录；iOS 沙盒不能直接使用这些路径。
- 现有 HTTP 接口按本机桌面应用设计。`CurrentUserProvider` 固定返回 `local-default`，桌面 API 地址默认 `localhost:8081`；它不是可直接暴露到公网的多用户同步服务。iPhone 上的 `localhost` 也不是电脑后端。
- 必须保留跨域语义：手记与日历双向可见；财务交易与账户余额同事务；日历收支统计与财务口径一致。移植时不能只复制页面表现。

## 3. 建议技术栈

| 层 | 建议 | 选择理由与边界 |
| --- | --- | --- |
| 语言与 UI | Swift、SwiftUI、Xcode | 原生触屏交互、系统导航与无障碍支持；新应用使用 SwiftUI 是 Apple 官方建议。[Apple SwiftUI](https://developer.apple.com/documentation/technologyoverviews/swiftui) |
| 并发与网络 | Swift Concurrency；需要联网时用 URLSession | 首版本地运行无需预设后端地址；未来同步由独立适配层承接。[Apple URLSession](https://developer.apple.com/documentation/foundation/urlsession) |
| 本地持久化 | SwiftData 作为首选评估对象，隔离在 Repository 后；复杂财务原子写入和迁移先做原型验证 | SwiftData 提供本地持久化和 SwiftUI 集成，但能否满足现有财务事务、版本控制与迁移要求，必须用样例验证后定案。[Apple SwiftData](https://developer.apple.com/documentation/swiftdata/) |
| 附件 | 应用沙盒文件目录；数据库只存稳定附件 ID 和元数据 | 对齐桌面端文件资产边界；写入采用临时文件、校验、原子移动与失败清理。 |
| 凭据与提醒 | Keychain；UserNotifications 本地通知 | 仅在确需凭据时启用 Keychain；用户授权后安排待办提醒。[Apple Keychain](https://developer.apple.com/documentation/security/keychain-services)、[Apple 本地通知](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app) |
| 测试 | Swift Testing 测领域规则和持久化；XCTest 做关键 UI 流程 | 覆盖金额、周期日期、手记投影、迁移与恢复；真机验证通知、附件和后台行为。[Apple 测试文档](https://developer.apple.com/documentation/xcode/adding-tests-to-your-xcode-project) |

部署目标、Xcode/Swift 具体版本以开发机与计划支持的最旧 iPhone 确认后锁定；不要仅为采用新 API 提高最低系统版本。先使用系统框架，第三方依赖按具体缺口引入。财务是手工记账；不预设银行卡自动抓取或 FinanceKit。

## 4. 建议架构与目录

```text
RecordAgent/
├── 开发前规划.md
├── RecordAgent.xcodeproj/       # 决策确认后创建
├── RecordAgent/
│   ├── App/                    # 启动、依赖组装、导航
│   ├── Features/               # Calendar、Finance、Library、Journal、Tasks
│   ├── Domain/                 # 纯 Swift 模型、规则、仓储协议
│   ├── Data/                   # 本地仓储、迁移、附件、未来同步适配
│   └── DesignSystem/           # 共用控件与视觉令牌
└── RecordAgentTests/
```

UI 不直接操作持久化模型；领域层不依赖 SwiftUI。日历、资料、记录共用每日手记的稳定 ID；任务与日历共用待办事实。金额、自然日、时区、周期规则在领域层集中实现。导航建议五个一级入口先以原型验证，若“记录”与“资料”重叠，再调整信息架构。

## 5. 数据与同步方案：开工前必须选定

| 方案 | 适用情况 | 代价 |
| --- | --- | --- |
| A. iPhone 独立本地数据（建议首版） | 先做可靠单机 App | 与桌面端暂不实时互通；需设计导入/导出路径和未来同步 ID |
| B. iPhone 与桌面端同步 | 从首版就必须跨设备查看和编辑 | 需要身份认证、TLS、可达服务、增量同步、冲突处理、附件传输和服务端运维；现有本机 API 不具备这些条件 |

建议先选 A，并在模型中保留稳定 UUID、版本、创建/更新时间及来源字段，避免将来同步时推倒重来。首版至少提供结构化备份导出与导入设计；财务与资料的附件、金额精度和删除状态必须能往返。若用户明确要求首版与桌面同一份数据，先独立设计同步架构，再编码业务页面。

## 6. 开发前检查清单

1. 确认五个入口的准确含义，尤其“记录”和“任务”的数据边界；列出首版必需操作与暂缓操作。
2. 确认数据方案 A/B、是否需要多设备同步、是否必须导入桌面历史数据，以及备份恢复范围。
3. 确认最低 iOS 版本、目标设备、横竖屏范围、应用名称与 Bundle ID、是否计划上架。
4. 画出导航与 5 个入口的低保真流程；明确空状态、编辑、删除、回收、提醒权限和导入失败反馈。
5. 从现有 Java DTO/迁移和 TypeScript 类型整理领域字段对照表；特别核对日期/时区、金额、版本号、附件与软删除。
6. 做两个小型技术验证：财务“写流水+改账户余额”原子性与回滚；资料“富文本+附件+备份恢复”。通过后锁定持久化实现。
7. 建立 Xcode 工程、测试目标和格式/静态检查；先完成一条纵向流程（新增待办→月历展示→提醒→完成），再扩展其余模块。

## 7. 当前待决事项

- “记录”具体指每日手记、生活记录，还是另一套记录类型？
- “任务”具体指待办清单，还是现有桌面端的自动任务？
- 首版是否要与桌面端共用数据，或只需一次性导入？
- 首版是仅自用安装，还是计划 TestFlight / App Store 发布？

以上决策会改变数据模型、服务端范围和开发顺序，应在建工程前确认并更新本文。
