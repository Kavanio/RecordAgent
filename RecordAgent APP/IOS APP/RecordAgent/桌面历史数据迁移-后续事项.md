# 桌面历史数据迁移（后续事项）

> 状态：推迟实施。当前阶段只开发 iOS 界面和 API 请求层，不迁移桌面历史数据，也不修改现有桌面本地数据。

## 已确定的产品要求

- 现有桌面历史数据未来要归属到当前用户的邮箱账户，供桌面端和 iOS 在同一服务端账户下访问。
- 邮箱是账户标识；服务端使用稳定用户 ID 作为业务数据所有者，不能仅靠客户端提交邮箱决定归属。
- 当前桌面“邮箱绑定”是本机资料，历史数据在本地 SQLite、文件资产目录及其他模块的本地存储中；它不是已完成的远程身份认证或数据同步。

## 后续实施前必须完成

1. 建立服务端多用户账户、身份认证、授权和数据存储；确定本机已绑定邮箱与新服务端账户的验证/认领流程。
2. 盘点需迁移的数据域、附件、版本及跨域关系，明确首批迁移范围和不迁移项；生成可复核的数量与完整性清单。
3. 设计一次性导入或增量迁移策略、稳定 ID 映射、重复导入幂等、冲突处理及回滚方案；导入前保留本地备份。
4. 在隔离测试环境验证账户归属、条数/金额/附件校验、跨域投影和失败恢复，再安排桌面端切换到同一服务器。

## 当前阶段边界

iOS 代码只依赖明确的账户与业务 API 契约，通过可控假服务验证请求和界面状态。不要为尚未确定的迁移格式或本地数据库路径在 iOS 端加入临时兼容逻辑。开展迁移工作时重新评审本文件，并与根目录及后端目录的 DOX 约束同步。
