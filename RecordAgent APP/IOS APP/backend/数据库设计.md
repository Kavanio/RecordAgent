# 业务数据库设计

> 状态：首版结构基线。完整建库 SQL 位于 `src/main/resources/db/migration/V1__initialize_business_schema.sql`，由 Flyway 在新建 PostgreSQL 空库上执行。账户、业务 API 与数据导入尚未实现。

## 设计原则

- PostgreSQL 数据库名及业务 schema 名均为 `record`，与桌面 SQLite 隔离。当前单文件 V1 是空库基线；后续结构调整须新增 V2、V3 等迁移，不再改写已应用的 V1。
- 主键使用应用生成的 UUID；`app_user.id` 是唯一的所有者标识。业务表保留 `owner_id`，涉及两个业务对象的关联使用 `(owner_id, id)` 组合外键，数据库直接拒绝跨用户绑定。服务查询仍必须从认证上下文取得用户 ID。
- 时间点为 `timestamptz`，自然日为 `date`，一天内时间为 `time`，用户时区为 IANA 名称；IANA 名称的有效性由应用层校验。金额统一为 `bigint` 最小货币单位，币种是三个大写字母。事务、版本条件更新和授权仍由应用层负责。
- 页面不是数据表。首页、个人总览和月历摘要按需从权威表查询，不存另一份可编辑的汇总事实。

## 领域与关系

| 领域 | 表 | 权威事实与设计依据 |
| --- | --- | --- |
| 账户 | `app_user`、`email_challenge`、`auth_session` | 邮箱与昵称规范化后唯一；密码、验证码和刷新凭据只存摘要。账户 ID 稳定，不以邮箱充当业务外键。 |
| 日历 | `calendar_entry`、`calendar_todo`、`todo_completion`、`calendar_schedule`、`calendar_preference` | `calendar_entry` 只容纳待办和日程；详情按类型拆表。周期完成按“实例所在周期”唯一记录。 |
| 财务 | `finance_account`、`finance_category`、`finance_transaction` | 账户余额与流水同事务更新；划账是同 `group_id` 的出入两笔。日历花销直接读取 `expense` 流水。 |
| 资料 | `record_tab`、`record_entry`、`record_tag`、`record_entry_tag` | `journal` 记录就是日历手记的唯一事实，不再创建双向同步表。软删除、归档和版本保留桌面语义。 |
| 学习 | `study_category`、`study_session` | 开始/结束时间为事实；学习时长和按日拆分在查询时计算。每个用户最多一个未结束时段。 |
| 文件 | `file_asset`、`record_file`、`calendar_file`、`user_media` | 元数据与 Blob 内容分离；按目标类型建绑定表，以组合外键校验用户归属。存储键绝不返回给客户端。 |

## 关键语义

**周期待办**：`event_date` 是生效起点；每日实例按自然日、每周实例按周一、每月实例按月初写入 `todo_completion.period_start`。每周发生日由 `recurrence_weekday`（1=周一）确定；每月固定在月末，数据库用 `31` 表示规则，实际发生日按当月最后一天计算。取消完成时删除对应实例行。完成状态不冗余存入 `calendar_todo`。

**日历投影**：日详情组合 `calendar_entry`、当日 `finance_transaction`、`record_entry(record_type='journal')` 与覆盖当日的 `study_session`；月摘要只读取有界标题和统计。资料中的每日手记直接使用 `record_entry.id`，不再沿用 SQLite 的 `source_reference` 双向投影。旧 SQLite 的日历花销在将来迁移时必须明确映射到财务账户和流水，不允许把它直接复制成另一套权威花销。

**财务不变量**：支出及转出不能让余额为负；同币种账户才可划账。数据库约束保证余额非负、金额为正、同用户关联、划账单方向至多一笔、每日收益去重；成对划账、币种一致、流水写入与余额变化由财务服务在单一事务中维护并测试。余额校准与划账不进入普通收支统计。

**文件生命周期**：`file_asset` 可处于 `pending`、`available`、`deleted`。上传后只在内容完成且校验通过时转为 `available`；绑定前同时校验目标对象、文件所有者和可用状态。解绑后的二进制清理须按服务端生命周期处理，不能只删数据库行。

## 与桌面 SQLite 的调整

1. SQLite 的文本日期、时间点、布尔和金额转换为 PostgreSQL 原生类型；UUID、组合外键及部分唯一索引提升多用户隔离和数据约束。
2. 不复制 SQLite 的 `daily_event.expense_detail` 和手记双向同步表，避免同一事实有多个写入来源。
3. 不复制多态 `file_binding(domain_type, domain_id)`；按目标类型关联，数据库可验证引用及所有者。
4. 不复制 Agent、Token 用量、本机自动任务通知状态；这些不属于首版 iOS 业务事实。自动任务的规则、执行和手机通知去重待该阶段确定后单独迁移。

## 实施与验收

迁移只在新建的隔离数据库和已备份的目标环境执行。空库应用单个 `V1`；重复启动应无新迁移。已执行合并前版本迁移的数据库不兼容这份 V1，须单独制定保留数据的迁移方案。上线代码前还需实现：账户注册/会话轮换和限流、条件更新的版本冲突、各类型详情完整性、财务同事务记账、投影查询和文件清理。桌面数据导入是独立后续阶段，须先确定账户认领、ID 映射和余额对账。

## V5 请求可靠性扩展

V1 基线表不改写。V5 新增 `finance_write_request` 与 `auth_rate_bucket`：

- 幂等表主键为 `(owner_id,request_id)`，请求摘要与首次响应快照随流水和余额同事务提交。响应缓存只用于重放，金额事实仍是流水和账户。幂等记录与对应流水共同保留，不按短 TTL 清理。
- 限流桶主键为 `(scope,key_hash)`，固定窗口用原子 UPSERT 更新，失败请求也提交额度；不保存 IP、邮箱明文。一小时以内的窗口策略保留一天后清理，不作为账户或业务事实。

验证覆盖 V1～V5 空库迁移、重复执行、并发幂等、事务失败回滚及共享限流。已有 V4 数据库通过 V5 正常升级，发布前仍应在锁定 PostgreSQL 版本与部署备份流程下验证。

## 手机任务追加迁移（2026-09-30）
