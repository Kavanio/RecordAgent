# RecordAgent 独立业务后端开发规划

> 状态：设计基线。目录固定为 `RecordAgent APP/IOS APP/backend/`；已建立独立 Spring Boot 工程、PostgreSQL/Flyway 底座、通用 HTTP 基础设施及单文件 V1 建库基线。账户、业务接口与部署尚未实现；领域结构见 [数据库设计.md](数据库设计.md)。本文继续用于安排开发和验收。

## 1. 目标与阶段边界

新后端是未来桌面端与 iOS App 共用的**业务数据权威**，首阶段只向 iOS 提供账户与业务 API。现有 `agent-backend/`、Tauri sidecar 和本地 SQLite 继续服务桌面端；两套数据在桌面迁移前各自独立，不自动同步。桌面业务改接新后端并完成历史数据迁移后，Agent 才作为独立后端或本地执行端通过受控业务 API 访问它。

首个可用版本交付邮箱账户、个人资料、首页按日和个人总览，以及与桌面业务语义对齐的完整日历：月摘要、按日详情、待办、日程、收支、手记、周期待办、学习记录只读投影、附件与必要设置。财务、资料、记录的完整工作台页面和自动任务留待后续阶段；首版日历依赖的账户、收支、资料与学习能力仍须真实实现，不能用演示数据替代。

本后端不运行 AgentScope、聊天、模型、工具审批、飞书渠道或桌面系统命令；不接受客户端直接访问 PostgreSQL。iOS 的 Debug 假服务继续用于客户端开发，Release 只有真实认证 API 接通后才能显示真实业务数据。

## 2. 架构与工程组织

先建立一个**单体部署、标准水平分层**的 Spring Boot 工程，延续仓库已使用的 Java 21、Maven、Lombok、Spring Web、Spring JDBC 与 Flyway，并为多用户认证引入 Spring Security；选择具体受支持的 Spring Boot/PostgreSQL 版本时记录兼容性并锁定，不把桌面 `agent-backend/pom.xml` 当作父工程。初期无需服务发现、消息队列或独立业务微服务。

```text
backend/
├── AGENTS.md
├── 后端开发规划.md
├── pom.xml                         # 独立 Maven 根工程
├── src/main/java/com/butvan/recordagent/
│   ├── RecordAgentApplication.java  # 根包启动入口
│   ├── controller/<module>/         # REST 控制器层（如 auth、todo）
│   ├── service/<module>/            # 业务服务接口（如 auth、todo）
│   │   └── impl/<module>/           # 业务用例与服务实现类
│   ├── repository/<module>/         # 数据访问与存储 Adapter
│   │   └── mapper/<module>/         # Spring JDBC RowMapper 映射
│   ├── entity/                      # 持久化行快照实体
│   ├── dto/<module>/                # 接口入参和出参 DTO
│   ├── security/                    # 安全过滤、Token 与上下文用户
│   ├── annotation/                  # 自定义注解（如 @ApiLog）
│   ├── aspect/                      # 切面实现
│   ├── handler/                     # 全局异常捕获与统一错误响应
│   └── filter/                      # 通用 Servlet 过滤器（如 RequestIdFilter）
├── src/main/resources/db/migration/ # PostgreSQL 专用 Flyway 脚本
└── src/test/                       # 单元、HTTP 与 PostgreSQL 集成测试
```

每个分层职责单一：Controller 只接收并校验协议数据、获取认证身份和返回 DTO；Service 层处理用例事务与业务规则；Repository 层访问权威数据库或存储 Adapter。文件和邮件供应商通过接口与 Adapter 隔离。服务端不导入现有 Agent Tool Adapter、`CurrentUserProvider` 的固定用户实现或桌面本地配置。

现有桌面 `daily/`、`finance/`、`record/`、`study/`、`file/` 的模型、测试和行为是**对齐输入**。逐域形成“规则/字段/错误/迁移”对照清单后实施；可移植的纯规则经依赖审查后再提取复用，SQLite SQL、桌面路径和 `/agent/...` 路由不能原样复制。

## 3. 数据与业务不变量

PostgreSQL 保存账户、业务记录、文件元数据和后续任务配置；附件二进制经 `BlobStore` 存储，首版可选受控服务器文件目录，部署时再确定是否使用对象存储。数据库与附件分别备份并验证可恢复性。所有业务主键使用稳定、不携带用户信息的 ID；业务表保存 `owner_id`，外键、唯一约束和常用查询索引包含适当的用户范围。服务层在每次读取、写入和文件下载时检查所有权，测试覆盖跨用户 ID 猜测与批量查询。

| 领域 | 首版权威事实与关键规则 |
| --- | --- |
| 账户 | 规范化邮箱唯一；同一邮箱的密码登录和验证码登录解析为同一稳定用户 ID。个人资料、头像与会话按用户归属。 |
| 日历 | 待办、日程、手记分别保存类型化字段；自然日、时间和 IANA 时区分开。一次性、每日、每周、每月待办沿用桌面发生日和完成规则；周一为周起点，月待办落在月末。 |
| 财务 | 金额以最小货币单位整数保存。账户余额与收支流水在同一事务更新；收入、支出与划账、余额校准的统计口径区分，支出不使余额为负。 |
| 资料与手记 | 日历手记和资料库的每日手记是同一业务事实；跨页面展示共用稳定 ID，附件只通过文件 ID 绑定。 |
| 学习记录 | 时段及其按日投影归 `study`；开始、结束、补录与跨日时长口径沿用桌面规则。首版先提供日历和个人总览需要的读取。 |
| 文件 | 元数据与业务绑定在数据库；二进制经受控存储 Adapter；上传、替换、下载和清理都验证用户与业务对象归属。 |

周期实例的完成状态、手记和跨域统计必须有单一事实来源。更新与删除用版本号避免静默覆盖；并发写入以数据库约束、事务和可识别冲突响应兜底。PostgreSQL 迁移脚本从 `V1` 独立开始，已应用的脚本不可改写；禁止执行桌面 SQLite 的 Flyway 脚本。首版字段、索引和事实归属见 [数据库设计.md](数据库设计.md)，实现 API 时继续核对边界案例。[Spring Boot 的数据库迁移配置](https://docs.spring.io/spring-boot/how-to/data-initialization.html)与[PostgreSQL 约束文档](https://www.postgresql.org/docs/current/ddl-constraints.html)可作为实现依据。

## 4. 身份、权限与 API 契约

账户流程按 iOS 已有 `AuthServiceProtocol` 对齐：发送注册/登录验证码、邮箱验证后注册、密码登录、验证码登录、会话续期、退出登录和当前用户查询。密码使用 Spring Security `PasswordEncoder` 的自适应哈希；验证码只存摘要、设有效期和单次使用语义，发送与校验都有频率限制。访问令牌短期有效；刷新凭据可撤销、轮换并按设备记录，服务端只保存凭据摘要。生产凭据来自部署环境或专用密钥存储，不写入仓库。[Spring Security 密码存储文档](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)

所有受保护请求先认证，再以服务端解析出的稳定用户 ID 进入应用服务。邮箱仅作登录标识，`ownerId` 不由客户端指定；资源不存在与越权访问不得泄露其他用户数据。注册、验证码、登录和附件上传应有独立限流；个人资料、财务和手记正文不进入访问日志。保留根目录规定的 `@ApiLog`，对敏感字段仅记录脱敏后的摘要和请求关联 ID。

API 统一采用 `/api/v1` 前缀，先以契约文档固定每个接口的方法、字段、响应、鉴权、分页和错误语义，再写 Controller 与 iOS DTO。建议按 `auth`、`me`、`calendar`、`finance`、`records`、`study`、`files`、`overview` 划分资源；不沿用桌面 `/agent` 前缀。最先定稿的客户端所需接口如下：

| 入口 | 必须支持的请求与输出 |
| --- | --- |
| 认证与个人资料 | 注册、密码/验证码登录、续期、退出、当前用户、昵称/头像；返回稳定用户 ID 和可供 iOS Keychain 保存的会话凭据。 |
| 月历 | 指定自然月的有界日期摘要、真实事项标题/标记及统计；不能把整月正文打包返回。 |
| 日详情 | 指定自然日的待办、日程、手记、收支、学习摘要与相关资料；来源失败可识别，正文按日或按 ID 读取。 |
| 日历写入 | 待办、日程、手记、收支的创建、更新、删除与待办实例完成；携带期望版本，返回更新后版本和业务 ID。 |
| 周期便签 | 查询所选自然周/月内已生效的周/月待办、实际发生日、完成状态和版本；完成操作复用待办实例接口。 |
| 首页与我的 | 按日快照、近七日趋势、账户个人总览及最近活动；统计口径来自各领域权威服务。 |
| 附件 | 受限上传、绑定、下载、删除；只返回稳定文件 ID 或受控内容接口，不暴露存储路径。 |

统一错误至少区分参数错误、未认证、无权访问、对象不存在、版本冲突、限流和服务暂不可用；建议标准 HTTP 状态加稳定业务错误码，错误文案由客户端本地化。日期采用 `YYYY-MM-DD`，时间点采用带偏移的 ISO 8601，时区采用 IANA ID；金额传整数分，分页提供上限。接口契约需与 iOS `AuthServiceProtocol`、`HomeDataServiceProtocol`、`CalendarDataServiceProtocol`、`ProfileOverviewServiceProtocol` 同步核对，协议中尚缺的编辑、删除和附件操作再补齐。以上资源分组为规划，具体路径和 DTO 以首阶段契约文档为准。

## 5. 实施顺序与验收门槛

| 阶段 | 工作 | 可复核的完成证据 |
| --- | --- | --- |
| 0. 契约盘点 | 对照桌面领域规则、iOS 模型和页面清单；确定首版数据模型、API、错误语义与未决项。 | 逐项对照表；首版 HTTP 契约；日历边界案例清单，经桌面与 iOS 两侧核对。 |
| 1. 工程与数据底座 | 建立独立 Maven 工程、Spring Boot 配置、PostgreSQL、Flyway、健康检查和隔离测试环境。 | 空库迁移和重复启动成功；测试库可自动重建；构建不依赖桌面 sidecar。 |
| 2. 账户与安全 | 实现邮箱验证、注册、两种登录、续期/退出、用户身份和授权、个人资料基础字段。 | 两个账户互不读取；验证码重放/过期被拒；注销后刷新凭据失效；iOS 可完成真实登录。 |
| 3. 日历纵向流程 | 完成月摘要、日详情、待办/日程/手记及周期实例、版本冲突；接入首页按日读取。 | 真正的 PostgreSQL 写入后，iOS 可完成登录→查看日历→新增待办→完成；月末、跨年、夏令时和并发更新测试通过。 |
| 4. 跨域补齐 | 完成日历收支所需财务账户与流水、资料手记投影、学习只读投影、附件、个人总览。 | 金额与余额同事务；手记单一事实；跨域统计一致；附件越权和失败回收测试通过；iOS 首版日历功能清单逐项验收。 |
| 5. 部署与联调 | 配置 HTTPS、邮件、数据库和附件持久化、备份/恢复、可观测性；在测试环境联调 iOS Release。 | 真机使用测试账户完成核心路径；重启后数据仍在；备份可恢复；无密钥入库或日志；异常和限流可观测。 |
| 6. 后续迁移 | 设计并演练桌面账户认领、SQLite/附件数据导入、稳定 ID 映射与重复导入；切换桌面业务接口。 | 数量、金额、附件和跨域投影对账；回滚演练成功；两端登录同一账户读取同一事实。Agent 拆分另立方案。 |

阶段 0～5 完成前，不宣称 iOS 具备真实跨设备共享。阶段 6 遵循 iOS 工程的[桌面历史数据迁移后续事项](../RecordAgent/桌面历史数据迁移-后续事项.md)，当前不改桌面代码与本地数据库。

## 6. 环境、发布与运维约束

- 本地和 CI 使用隔离 PostgreSQL 实例执行迁移与集成测试；测试凭据和数据不得指向真实用户环境。生产连接、邮件、令牌密钥通过环境配置注入，并分别限制权限。
- 部署前明确数据库版本、备份保留与恢复目标、附件存储位置、HTTPS 终止、域名、邮件供应商和成本；这些尚未定案，不写死在代码或规划中的默认值。
- 数据库迁移与应用发布配套；先验证迁移、备份和兼容窗口，再部署新版本。健康检查只暴露必要状态，不返回凭据、内部路径或用户数据。
- 记录请求关联 ID、错误码、响应时间和必要的审计事件；对邮箱、令牌、财务与手记内容脱敏。监控认证失败、数据库连接、邮件队列、附件失败及备份结果。
- 每阶段执行格式/静态检查、单元测试、真实 PostgreSQL 集成测试和构建；公网部署前增加认证、越权、文件上传与限流的安全验证。

## 7. 开工前仍需决策

1. 服务器部署位置、域名、PostgreSQL 托管方式及环境分层。
2. 邮件发送服务、附件存储 Adapter 与备份/恢复目标。
3. 会话有效期、设备管理、密码找回与账户注销的数据保留规则。
4. 首版日历细项和 API 契约的逐项核对结果，尤其旧日历花销与新财务流水如何处理。
5. 桌面端改接的时间点、账户认领及历史数据迁移窗口；这些不阻断新后端前五阶段开发。
